## 一、现有报告可以保留什么，需要改什么

这份报告有 **8 张按 GPU 划分的工作表、691 条性能记录和 138 条功能记录**。现有的用例名称、分支、指标、单位、主机环境和问题备注都有价值，按 GPU 阅读的方式也可以保留为自动生成的视图。



主要需要解决以下问题：

| 现有情况 | 建议调整 |
|---|---|
| 没有明确的镜像 digest 字段，主要靠 Case Name、Branch、HPC Version 定位 | 每条执行绑定 **App、HPC version、实际 digest、测试配置 commit** |
| 环境放在每张 GPU 表的页首 | 环境生成独立的 `env_id`，每条结果引用，允许同一张报告出现不同环境 |
| 没有完整的选测范围 | 增加覆盖计划，列明哪些组合选测、哪些未选、原因是什么 |
| `/` 同时表示不同含义 | 执行状态、数值、缺失原因分开保存 |
| 本期、上期、另一 GPU 的结果横向排列 | 每次测量单独保存，比较时引用相应的历史结果 |

其中两个问题很具体：

- `C500!F121` 的 `/` 表示没有上期基线，备注是“新增支持 C500”；但 `C600!E159:G159` 的 `/` 对应“测试失败 MC3-16560”。**导入时不能把 `/` 全部理解成未测。**
- `X203` 同一条测量，同时与上版本、同版本 C500 比较。因此，应该保存“一次测量、两次比较”，避免重复统计成两次执行。

## 二、先区分两类 QA 批次，使用同一套格式

配合你们这次发布方式调整，建议报告顶层增加一个“验证类型”。

| 验证类型 | 测试对象 | 环境与目标 | 结果用途 |
|---|---|---|---|
| **月度 App 发布验证** | 本月报名 App 的候选镜像 | 当月固定基线 | 判断这个 App 本期是否发布 |
| **组件兼容验证** | 批次创建时，各 App 最新正式版本的选定镜像 | 待验证的 SDK、Driver 或其他组件版本 | 记录已有 App 对新组件的兼容证据 |

这样，**一份 SDK 兼容报告可以包含不同 App 各自不同的 HPC version**。没有报名重发的 App，继续使用自己的正式版本参与兼容验证。

`HPC version` 可以保留，但应当与 App、镜像一起记录，不能承担唯一定位的作用。报告顶层更适合放：

- 验证批次 ID、类型、时间。
- 目标组件及精确版本。
- 月度基线或本次验证环境。
- 测试范围和最终结论。

例如，原表中的 `Host SDK Version = 3.10.0.27` 和 `HPC Version = 3.10.0.7` 本来就是不同字段，新格式应继续保持这种区别，而不是都归到“3.10 版本”。

## 三、QA 不必测所有镜像，但要明确选测策略

### 1. 先列有效组合，再选择本期测试集合

范围应当来自 **实际交付的镜像，以及 Owner 声明支持的运行环境**，不用把所有 OS、CPU、GPU、Torch、Python 随意做笛卡尔积。

例如，同一个 digest 可以分别在 C500、C600 上测试；不同 CPU 架构或不同 Torch/Python 的镜像，则应保留各自的身份。

建议分三层安排：

| 层级 | 建议覆盖方式 |
|---|---|
| **冒烟** | 容器启动、设备识别、库加载、小算例。优先自动覆盖新增镜像和新增平台；缺资源的明确标未测 |
| **功能** | 每个 App 选择主力组合跑核心回归，再补新增架构、GPU、OS、框架组合及已知问题相关组合 |
| **性能** | 选择少量固定的代表环境和工作负载，保持规模、卡数、die/拓扑等条件可比，独立记录性能覆盖范围 |

组合很多时，可以用 pairwise 等组合测试方法辅助挑选样本，但它不能保证发现更高阶的组合问题，也不能据此把未测组合标成实测通过。[CSRC](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/combinatorial-methods-in-testing/interactions-involved-in-software-failures?utm_source=chatgpt.com)

### 2. 报告应该这样表达抽样结果

下面是模板中的假设场景，同一个 App/HPC version 有 6 个镜像与运行环境组合：

| 镜像 | 变体概要 | 运行 GPU | 功能证据 | 性能 |
|---|---|---|---|---|
| D1 | x86、Ubuntu 22、Torch/Python 组合 A | C500 | 本次实测通过 | 本次未测 |
| D1 | 同一个镜像 | C600 | 本次实测通过 | 本次已测，单独比较基线 |
| D2 | ARM 变体 | C500 | 未选测 | 未测 |
| D3 | 另一容器 OS | C500 | 未选测 | 未测 |
| D4 | 另一 Torch/Python 组合 | C500 | 引用同条件的历史实测通过 | 本次未测 |
| D5 | 另一组 OS、Torch/Python | C600 | 未选测 | 未测 |

这时可以报告：

> 功能验证：本次实测 2/6 个组合，引用历史同条件证据 1/6，其余 3/6 未测。
>
> 性能验证：本期只选择 C600 的一个代表环境，已执行并完成基线比较。

**“本期选测计划完成”与“全部支持组合都测过”是两个统计口径，应该同时保留。**

历史复用也要有明确条件：镜像、影响结果的运行环境、目标组件版本、命令、测试定义和数据集一致。**如果本次目标是新 SDK，就不能拿旧 SDK 下的 PASS 直接当作新 SDK 的兼容通过。**

## 四、报告格式：4 张核心表，加一张性能比较表

我建议采用下面的结构。**这些字段大部分由网站或脚本生成，QA 不需要手工填写几十列。**

| 表 | 一行代表什么 | 主要内容 | 谁维护 |
|---|---|---|---|
| **Summary：汇总** | 一个批次的总体情况，可进一步按 App/GPU 汇总 | 目标版本、选测数、实测数、未测数、失败数、性能待审项、发布决定 | 系统汇总，负责人确认 |
| **Coverage：覆盖计划** | 一个镜像在一个目标环境上的一个测试项或固定用例集 | App、HPC version、digest、环境要求、测试层级、选测/复用/未选、原因 | 系统预填，Owner/QA 确认 |
| **Results：执行结果** | 一次实际执行 | 执行 ID、用例、实际 digest、环境 ID、命令、配置版本、结果、时间、日志、Issue；性能用例附指标值 | 脚本采集，QA 确认异常 |
| **Environments：环境** | 一份计划要求或实际采集的环境快照，两者明确区分 | 主机与容器环境、SDK、Driver、GPU 等 | 自动采集为主 |
| **Comparisons：性能比较** | 一次测量与一个基线的比较 | 当前结果 ID、基线结果 ID、比较类型、变化率、阈值、审阅结论 | 系统计算，QA 审阅 |

第五张表是因为你们现有 X203 已有双基线需求。它不需要增加 QA 的重复录入，也不需要每换一个 SDK 就新增一列。

### 几组字段一定要分开

**镜像身份与运行环境：**

- 镜像：完整仓库引用、digest、构建 commit、构建 SDK、镜像内 OS/框架信息。
- 实际环境：宿主 OS、kernel、CPU 架构、GPU 型号与数量、Driver、实际加载的 SDK、Torch/Python。
- 性能相关的卡数、die/拓扑、CPU/NUMA 等条件，按用例需要采集。

**构建 SDK 与实际运行 SDK：**

验证“旧 App 镜像是否兼容新 SDK”时，需要确认测试进程实际使用了目标 SDK。只填写“宿主机安装了新 SDK”，不足以说明容器里的程序已经使用它。

如果为了换 SDK 重新构建了镜像，应记录为新的构建/镜像验证，不能把它直接当作旧 digest 的兼容证据。

**多架构镜像的整体 digest 与实际平台 digest：**

如果 Harbor 中使用多架构 image index，建议同时保存 index digest 和本次真正运行的 platform manifest digest。OCI 的 image index 可以指向不同平台的具体镜像，单独保存整体 index 不足以直接看出这次跑的是哪一个平台镜像。[specs.opencontainers.org](https://specs.opencontainers.org/image-spec/image-index/?utm_source=chatgpt.com)

### 状态与性能数值也要分开

- 执行结果使用固定枚举，例如 `PASS / FAIL / ERROR / TIMEOUT / CANCELLED`。
- 没有执行的项留在覆盖计划中，显示“未选测”或“待执行”，不制造执行记录。
- 性能数值保存为数字，缺失留空，原因单独记录。
- `max/min` 改成明确的指标方向，例如 `HIGHER/LOWER`。
- “执行成功”“性能达到要求”“批准发布”分别判断。

原报告里已经有“移除某环境变量导致性能变化”的备注，例如 `C500!H112`。这说明比较前必须检查命令、环境变量、数据集及其他运行条件。**跨 GPU 对比可以保留，但应标明其目的，不能混成同平台的 SDK 性能回退。**

## 五、自动化与存档怎么做，才能保持简单

### 1. 让 QA 主要做选择和确认

建议流程是：

1. **网站生成批次和预填计划。** 从报名候选或正式发布清单取得 App/HPC version 和镜像，解析变体属性。
2. **QA 选择代表组合。** 确认本次执行哪些、复用哪些、暂不测试哪些，并填写必要原因。
3. **执行脚本采集事实。** 保存实际 digest、环境、命令、配置 commit、数据集版本、数值和日志。QA 补充失败分析、Issue 和必要的人工结论。
4. **网站导入结构化结果并生成报告。** 第一版可以导入固定格式 Excel/CSV，后续让流水线上传同一套字段的 JSON。

可以继续采用你之前提出的 **Harbor → commit → Gerrit `app_info`** 方式解析镜像信息，QA 无须手工把 digest 对到某个 build 行。但执行完成后，应保存当时实际使用的配置和环境，后续查历史结果直接读取这些事实。

自动导入应依赖固定字段、枚举和关联校验，不依赖单元格颜色、自然语言备注或 AI 猜测。模板里也增加了 `schema_version`，方便以后升级格式。

### 2. 数据库第一版只需要补两类记录

**Excel 分成五张表，不意味着数据库也必须新建五套表。**

可以继续复用现有 App、镜像、`app_info` 和正式发布记录，补充：

- **验证批次 `qa_batches`**：验证类型、目标组件版本、固定的测试范围、选测计划。
- **执行记录 `qa_attempts`**：每次实际测试的身份、输入、环境、结果和证据引用。

计划、环境和比较详情可以先作为结构化 JSON 保存；经常查询的 App、HPC version、digest、组件版本、GPU、用例、时间、结果使用独立字段，便于筛选。暂时没有必要建设复杂的覆盖率推断系统。

### 3. 发布记录可以替换，测试执行记录应追加保存

这与你前面第 4 点的决定可以同时成立：

- **正式发布记录**：解锁后删除旧封存，重新发布替换。
- **测试执行档案**：保留当时实际测了什么、结果怎样。重测新增一条，不覆盖上一次。

例如，同一个 digest 在 SDK A 上通过、在 SDK B 上失败，这两条都需要保留。否则以后很难判断兼容性从哪个版本开始变化。

目前检查的这版代码中，QA 附件按 `release_id` 保存，重新上传会覆盖原文件；若要承担长期兼容查询，需要调整成按批次或执行记录追加归档。[现有 QA 附件保存逻辑](https://github.com/zzwz02/hpc-release-system/blob/c5a29dafb9a9315579f06aec35008a337cf881e6/app/repositories/qa_repo.py#L45-L68)

每次归档至少应能找到：

- 原始报告和结构化结果。
- 实际命令、配置来源、环境快照。
- 日志、性能原始数据和相关 Issue。
- 数据集或模型的版本/校验信息。

正式发布及兼容证据引用的镜像，也应纳入 Harbor 保留规则，避免记录仍在而镜像已经被清理。Harbor 的保留策略会影响哪些 artifact 被保留，需要与这里的归档范围一致。[Create Tag Retention Rules](https://goharbor.io/docs/edge/working-with-projects/working-with-images/create-tag-retention-rules/?utm_source=chatgpt.com)

### 4. 历史查询与兼容验证共用这些记录

你之前担心 QA tab 信息重复，这里可以明确各自职责：

- **发布 App 列表**：查看正式版本、交付镜像和验证范围摘要。
- **按 digest 查询**：查看该镜像在不同环境、组件版本下的执行时间线和证据。
- **组件兼容验证**：创建新验证批次、选择范围、跟踪失败和未测项。

它们引用同一套执行记录，避免分别维护一套“兼容通过”结论。查询时，某个环境的 PASS 只能说明那个环境下的相应用例通过；没有匹配证据就显示未验证。

## 六、旧报告怎么处理

**旧报告先完整保存，不要求 QA 把全部历史记录补成新格式。**

现有记录仍然可以按 Case、Branch、GPU、SDK/HPC version 查询，并保留源工作表和行号，例如 `C500!252`。没有记录 digest 的，标记为“历史报告，未绑定镜像”。

不要使用今天某个 tag 对应的 digest，反填成“当时测试的镜像”。只有能从当时的 CI 日志、测试日志等证据确认，才补充绑定关系。

下一轮开始，先由网站预填镜像身份和覆盖计划，再让测试脚本输出环境与执行结果。这样 QA 的新增工作主要是**确定选测范围、确认结果、解释异常**，报告汇总与后续查询都可以逐步自动化。
