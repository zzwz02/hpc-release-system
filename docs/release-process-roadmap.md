# 发布流程改进建议

本文件是功能规划建议，不是已上线能力清单。依据 2026-09-05 对当前代码和 `release_system.db` 的只读检查；业务进度会继续变化。没有调用应用建库/迁移、文档生成、真实 Jira/Gerrit 写入或 AI 服务。

## 数据口径

数据库用 SQLite URI `mode=ro`、`PRAGMA query_only=ON` 和读取事务检查。只汇总业务字段，没有导出用户名、口令哈希、会话 token、日志正文或助手对话。

| 观察项 | 结果 | 如何解读 |
| --- | --- | --- |
| 全局 App / 周期 | 127 个 App；3.8.0 已锁定，3.9.0 未锁定 | 已有真实跨周期维护需求，不宜继续依赖分散表格 |
| 3.9.0 快照决策 | release 80、cicd_only 20、stopped 27 | “全部 App”“计划发布”“CICD 运行”必须分开统计 |
| 3.9.0 Owner | 发布范围涉及 19 位 Owner，25 个发布 App 尚未确认 | 可以直接形成按责任人分配的待办，而非只展示总数 |
| 3.9.0 文档资格 | 按当前代码重算 47 个满足文档收录条件，33 个尚不满足 | 缺项会使计划内 App 从生成文档中消失，锁定前需要明确核对 |
| 3.9.0 QA 记录 | 80 个发布 App 均为 not_checked，本周期无 QA 日志 | 只能说明系统未记录结果，不能断言同事尚未开展测试 |
| 测试说明规模 | 发布范围内 283 条非 obsolete 的 test_docs，其中 9 条缺少数据集/内容/查看方式/标准中的至少一项 | 这是说明条目数量，不是已执行用例数量；单 App 状态无法表达细粒度覆盖 |
| 3.9.0 信息缺项 | App 类型缺失 7、短描述缺失 7、介绍缺失 6、镜像使用说明缺失 6 | 缺项互有重叠，不能直接相加；适合模板和逐项定位 |
| app_info 来源 | 本期 80 个发布 App 均有 app_info 和非空 commit_id | 源版本追溯已有基础，优先补执行证据和变更影响，不必重建来源机制 |
| 草稿新鲜度 | 最新 data 草稿生成于 2026-08-12；与当前快照相比，52 个共同 App 的业务字段不同，另新增 3 个快照 | 产物与当前数据已经发生偏离，需要显式版本/过期提示 |
| 周期差异 | 与 3.8.0 快照相比新增 12 个 App 快照，共同 App 中 2 个版本字段变化、22 个发布决策变化 | 这是快照字段差异，不直接等于正式“新增/停止发布”清单 |
| CICD 历史 | 124 条申请，当前 1 条 pending，尚无 pending/returned 交付 | 当前主要瓶颈证据偏向信息确认、QA 记录与产物一致性，暂不需要先建复杂审批中心 |
| Owner 确认变化 | 本期 81 条 owner_confirm_invalidated 审计记录 | 确认失效机制已经存在；应提升变更说明、通知与重新确认体验 |

文档资格在内存中调用当前 `_missing_items_for()` 和 `qualifies_for_docs()` 计算，没有回写 `missing_items`。这不是对旧 final 产物的重新判定。

草稿差异比较同 App 的版本、Owner、确认、决策、QA、文档、测试说明、社区、Sanity、芯片和描述字段，排除仅同步时间变化；比较对象为数据库 `artifacts.kind=data` 中保存的快照，不表示 52 个 App 都曾收录进 Markdown。

另发现 `audit.ts` 中仍有 348 条带 UTC offset 的旧时间，`artifacts.generated_at` 中有 1 条。这是时间迁移/展示一致性问题，不能继续在文档声称历史库已经全部统一，也不应在此次文档任务中直接修数。

## 第一批：个人待办与统一 App 发布详情

### 在现有工作台增加“我的待办”

现状已有 App 缺项、Owner 确认、QA 状态、CICD 请求和通知，但需要跨页检索。新增待办视图直接从现有事实推导，不另建一份可独立修改的“是否完成”字段。

- Owner：待补字段、待确认、因 app_info 变化需要重新确认、被退回的配置/交付事项。
- QA：待领取、待执行、待复测、被阻塞且需要 Owner 补资料的项目。
- RM：计划内但未满足文档条件、尚无 QA 结果、等待审批、产物过期、临近 deadline 的事项。
- SPD：待交付、待补原因/材料、需要重新派发的申请。

每项给出 App、release、具体原因、责任人、期限和直达编辑位置；一键“只看我负责”“按阻塞原因分组”。提醒先做站内聚合和手动复制摘要；邮件/IM 摘要作为可配置订阅，收件范围、频率和去重明确后再接入，避免逐字段通知。

**验收：** 同事从待办点击后直接进入正确 release/App/字段；完成源操作后待办消失；切换账号不残留他人待办；同一缺项不重复计数。

### 建立统一详情链接和周期日历关系

当前共享选择状态保存在浏览器 UI store，时间线和 release 又是分离表。新增稳定的 release/App 深链接，并让时间线条目显式关联周期，减少同事发截图或描述“我当前选的那个版本”。

保留清晰事实归属：全局 App 是身份和责任入口，release 快照是本周期计划与确认结果；Gerrit 提供 app_info，QA 执行提供结果，最终发布包保留交付事实。新增字段必须说明在哪一处维护、其他页面如何读取。

**验收：** 分享链接后接收者打开的是同一 App/周期；发布日、freeze 和 doc deadline 的来源明确，修改不在两张表间漂移；界面同时展示“计划范围、文档资格、QA 资格、CICD 交付”各自状态。

## 第二批：QA 执行与问题闭环

现有 QA 状态、测试命令表、日志上传和 AI 建议保留。新增结构化 Test Run，让 QA 能记录具体做了什么、证据是什么。

- 测试计划按 release + App + app_info commit + 测试条目 + 芯片/架构/环境形成基线。
- 执行记录包含执行人、时间、结果、日志或 Jenkins build 链接、环境与复测关系；同一用例可以多次执行，保留历史。
- 将“未执行、通过、失败、跳过、阻塞”与 App 汇总状态分开；跳过/阻塞必须有原因，防止把缺数据当通过。
- 从 Jenkins 导入已知结构化结果，无法匹配的记录进入待核对列表；日志解析与 AI 只辅助匹配，不独立批准发布。
- QA 问题关联责任人、严重程度、影响范围、Jira、解决版本和复测记录；缺说明的问题可退回 Owner，双方在同一对象上补信息。

单个 release 的一份日志不足以承担执行证据历史。可保留现有上传入口，同时为每次上传保留不可覆盖的附件版本和来源；不要为此重复存储不必要的大文件。

**验收：** 任意 App 的 QA 汇总能展开到每个基线项及最近有效执行；失败有证据、有责任人、有复测；换 commit 后能辨识旧结果适用范围；不能用一份过期日志覆盖新证据。

## 第三批：发布前检查与例外批准

当前 `qualifies_for_docs` 与 `qualifies_for_final` 分离，最终锁定不要求全部 QA 通过；`has_issues` 也可满足现有 QA 门槛。不要只在按钮前增加一句确认文本。

增加发布检查页，列出完整计划范围、拟收录范围、QA覆盖、未完成请求、未确认信息、有效例外和产物版本。每个未满足条件的 App 必须有明确处置：补齐、从本期范围移除，或申请有责任人与理由的例外。

建议分开“生成文档草稿”和“正式批准发布”。正式批准保存 QA 签认、RM 决定、基线版本及例外清单；Owner 继续负责信息确认，不把三种职责混为同一 checkbox。

`has_issues` 细化为已知问题及其接受依据：影响、缓解方式、批准人、适用版本和到期范围。新增门槛先以预检查模式展示影响，经团队确定政策后再成为硬阻塞；不要追溯改变已发布版本的结论。

**验收：** 计划内 App 不会无解释地从交付包消失；批准记录能追溯到当时的 QA/文档/配置版本；批准后变更使检查失效；例外只对明确版本有效。

## 第四批：基线差异与可追溯发布包

### 扩展已有差异功能

系统已有 app_info diff 和 Owner 确认失效。补足“本次保存相对上次确认”“当前周期相对已发布基线”“生成产物相对当前数据”三个比较对象，不把它们合成一个 diff。

展示版本、芯片、命令、文档、发布范围与 QA 影响。变更指向受影响测试和待重新确认事项；仅时间戳变化不触发业务提醒。对既有 Owner 确认可记录具体确认的内容版本，避免“确认过”脱离所确认的数据。

### 让草稿过期可见、发布包可追溯

当前 `(release_id, kind)` 只留一份产物。增加内容 revision/hash 和生成依据；工作台有变更时显式显示“草稿落后于当前数据”，并能查看差异、重新生成。

正式交付包保存不可覆盖的版本、生成者、基线、各产物 checksum、QA/例外清单与相关请求。下载页面区分“当前草稿”和“已批准包”。重开发布产生下一修订，而不是让已发出的包失去系统记录。

正式 release note 从已批准基线比较生成“新增/版本变化/恢复/停止”，完整清单另列；缺少文档条目不能自动算作停止。C500/X201 导出固定目标 release 与芯片范围，避免默认选择旧 final。

**验收：** 当前数据变化后旧草稿有明确过期标记；相同输入生成结果可核对；任一历史交付包可重新下载并确认依据；解锁不抹掉对外已发布修订的历史。

## 表单和日常效率的配套改善

将“已有文档字段”升级为受控模板：按 App 类型/产物类型预填说明结构、示例格式和必填项，逐字段校验并直达修复。已有“从其他版本复制”继续使用，但展示来源和差异，不复制确认状态或测试结论。

为同事提供按 App/版本/芯片/Owner 查询的轻量目录、命令与已知问题入口。优先把现有数据连接起来，不新建第二套 App 台账或 WIKI 发布清单。收藏筛选和批量处理可在上述事实源之上逐步增加。

## 实施顺序与基础修复

先解决代码审查已发现的并发覆盖/锁定竞态、身份缓存隔离和 Jira 幂等；否则新的待办、签认和发布包仍可能绑定错误状态。同步修复事件循环阻塞，并处理开发账号和会话生命周期。

业务功能先做“个人待办 + 统一详情链接 + 草稿过期提示”，随后做 QA Test Run 和问题闭环，再引入正式发布检查、例外与不可覆盖发布包。数据库、权限、前端展示使用同一模型，不把审批结果、任务状态和发布资格各维护一份。

对现有已锁定 release 保留原始产物与历史语义。新增表和关系先在副本回填验证；不知道历史执行人/环境/证据的字段标记未记录，不用脚本推测补齐。
