# Jira 知识学习

RM 在“JIRA agent → 知识学习”选择工单。左侧默认列出 agent 处理过的 Jira，也可按编号或 JQL 添加历史 Jira。学习不限制 component，不改工单状态、不发评论。多选后创建一个联合学习任务，单选使用同一流程。同一 Jira 可以参加不同任务；重复提交同一次请求不会重复创建。提交后立即进入任务页，后台读取工单和对话、登记文件目录；无权访问或获取失败的工单会显示原因，保留其他已取得的材料。

左侧可切换 Jira 和学习任务，点击 Jira 可查看它参与过的任务。右侧按知识点展示提案，每次展开一项；材料和对话可折叠。补充要求进入下一轮；退回提案时填写意见，网站一次完成退回和修订排队。旧提案、审核记录和材料不删除。刷新材料会创建关联的新任务，旧对话只读。

## 知识来源

正式维护来源是独立 `jira_agent_skill` 仓库。网站读取固定提交生成 patch，另从对应分析 app-server 复制项目 `AGENTS.md`、skill 和文本引用作为学习参考。不会复制授权、配置、SSH 凭据或原有任务目录。线上未入库内容不会自动加入提案。

线上采集失败时可重试，或由 RM 明确勾选“仅参考仓库版本”。同一任务的补充轮沿用 Jira、仓库和线上 skill 快照。需要更新材料或基线时，点击“重新采集并学习”创建新任务，原记录保留。Agent 先获得全部案例入口和知识索引，再按需读取正文。目录保留各参与者的对话、失败尝试和各轮结果；准备中、尚未读取与读取失败分别处理，只有影响判断的实际读取失败才列为材料缺口。

学习同时比较各案例的验证结果、条件差异和反例，避免把个案步骤写成普遍要求。提案说明原规则的缺口及修改会改变的判断；条件过宽或规则冲突时优先改写原文，入口不清时补充提示与引用，详细条件保持一处维护。同一任务按知识点统一生成修改，不逐张生成补丁后拼接；同一文件的修改集中在一条提案。验证说明区分已完成的材料核对与候选 skill 待验证的行为、场景及通过条件。

每条提案可包含一组关联 Markdown 文件，保留修改前后全文、目标提交和依赖哈希。依赖由提案明确声明，仅包含其规则或实现会影响修改成立的已有文件；网站不沿 Markdown 导航链接自动扩展。目标文件仍单独校验基线，目标或依赖文件变化时提示重新整理，无关文件变化不阻止审核。旧提案保留生成时的依赖与审核记录，需要调整依赖范围时重新整理并审核。相同文件上的其他待审核、已通过提案给出重叠提示，不能据此直接判定语义重复或冲突，仍由 RM 判断。无需更新时保留原因，不要求审核。

## 审核和人工更新

通过只绑定当前提案版本，不修改仓库。维护人员在“人工更新与验证”中选择已通过提案，下载一个补丁包，包含 changes.patch、基线和验证说明。网站检查文件重叠、依赖冲突和基线变化。人工检查、应用、验证并提交后，可统一登记多条提案的同一个提交。登记入库时，网站核对提交属于配置的正式分支，并检查所有目标文件内容确实对应提案；只修改同名文件的无关提交不会通过。

实际应用时调整了内容，可填写提交及说明，点击“按实际提交重新审核”生成新版。新版需要重新批准。网站不提供代码编辑、提交、push 或部署操作。

独立测试用于验证，不作为联合学习输入。可关联原案例复测或其他场景验证，网站展示测试评价并核对保存的实际 skill 内容。版本不匹配或提案已修订时，会提示该记录不能证明当前修改有效。候选 skill 应在独立验证环境中使用，网站不会自动切换正在运行的分析服务。

入库和部署均在“人工更新与验证”中登记。部署时选择已入库提交、填写目标服务、结果和备注；同组相同提交的提案共享记录，一次部署只需填写一次。每次登记都保留，失败后再次部署可追加记录。人工填报标为“人工登记”，不表示系统已回读验证；部署失败不会撤销入库记录。

## 配置

学习使用独立 Codex app-server 和 CPU 工作目录，队列串行执行；启动脚本采用只读沙箱。配置依据见 [Codex 沙箱说明](https://learn.chatgpt.com/docs/agent-approvals-security#sandbox-and-approvals)。网站保持单 worker；材料解析按需交给有并发上限的工作进程，不占用分析服务队列。学习端不需要 Jira token、实验机 SSH 凭据或 GPU。

在网站的 `release_system.conf` 配置 `[jira_learning:<组名>]`，模板见 `release_system.conf.example`：

- `CODEX_WS_URL`、`CODEX_WS_TOKEN`：独立学习服务。
- `WORKSPACE_ROOT`：学习知识包下的 `workspaces` 目录。
- `TURN_TIMEOUT_SECONDS`：每轮总时限，重启不重新计时。
- `REPOSITORY_REF`：本地已获取的正式分支，例如 `refs/remotes/origin/main`。
- `MODEL`：可选，空表示使用服务默认模型。

`JIRA_LEARNING_REPO_ROOT` 指向独立仓库检出目录，默认是发布系统同级的 `jira_agent_skill`。网站只读该目录，不自动 fetch。登记提交提示版本不存在时，由维护人员更新这个缓存后重试。整节未配置时不能发起学习，但分析服务继续工作。

Agent 按目录取材，用户无需参与读取。学习对话保留材料引用，提案的来源证据默认折叠，需要核查时在原位置展开；长文本和 PDF 分段查看。压缩包仅在访问时列出成员。已读取内容和解析结果会缓存，证据与读取范围单独保存，不反复打包整份资料。

学习技能在 `deploy/jira-learning/pack/`。采集快照在 `JIRA_AGENT_DATA_DIR/learning/`，队列、轮次、提案和审核记录存于 Jira agent 数据库的独立表。

任务创建接口 `POST /api/jira-agent/learning/jobs` 接收 `issue_keys`，单选和多选均返回 `{job, reused}`。JQL 用于添加候选 Jira，再按编号创建学习任务。提交登记统一调用任务下的 `/publication`，部署登记调用任务下的 `/deployments`；旧的单提案登记接口仅转发到同一业务逻辑。退回修订使用审核接口，补充学习使用任务消息接口。

运行时材料统一存入各任务的 `materials/sources.db`；来源清单只保留概览、知识版本和引用。读取旧 JSON 材料时，在入口原子转换，保留原文件、来源 ID、已缓存内容及读取记录；转换中断可以重试。快照文件按内容哈希命名并校验，原始材料与引用片段仍分别保存。旧部署记录按原 ID 导入共享事件表，保留全部历史登记；旧字段和旧表保留用于历史兼容，新流程不再写入废弃数据。

## 更新分析服务的 skill

部署单独检出指定提交，不使用子模块，也不从发布系统中的旧打包副本取版本。目标目录应在空闲时更新：

```bash
SKILL_REPO=/path/to/jira_agent_skill \
SKILL_COMMIT=<完整提交SHA> \
PACK_DIR=/path/to/hpc-jira-agent \
  deploy/jira-agent/sync-pack.sh
```

脚本读取固定提交，保留任务目录，写入 `.skill-version.json` 供后续采集确认版本。发布系统代码和知识版本分别更新；更新网站不会自动同步 skill。

## 失败与恢复

排队任务可直接取消。运行中先请求远端中断，确认停止后显示已取消。网站停止只断开连接，恢复后查询原轮次并接续；状态不明时显示“核对远端状态”，保留队列位置，不重复启动。

错误保留阶段、原因和已有结果。全部材料采集失败时重新采集；输出不合约时保留原始输出，再开补充轮整理。历史任务和已被新版替代的提案保留，旧数据缺少文件基线时要求重新整理后审核。

历史远端线程未注册材料工具时，先核对并接收已经启动的轮次；下次补充学习使用支持材料工具的新线程，传入历史用户要求及已有结果，继续沿用固定材料和知识基线。网站上的任务、轮次、提案及审核历史保留。
