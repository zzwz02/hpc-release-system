## 一、哪些重复，哪些应保留？

| 当前入口 | 实际回答的问题 | 建议 |

| 发布 app 列表 | 某个发布周期成功发布了哪些 App？ | 保留，作为“发布记录”的周期筛选 |

而且，重复入口已经产生了规则差异：**基线页面会回查迁移留下的历史成功发布，组件页面没有这层回查。** 所以某个 App 可能在一处出现，在另一处消失。应该统一这个选择规则。

## 二、我建议整理成两个入口

### 1. 兼容性验证：QA 日常使用的主入口

将当前“兼容性测试基线”和“正式版兼容验证”合并。

**默认范围：每个运行中 App，选取最近一次有效、成功的发布。** 不同 App 可以来自不同月份；后续未报名或发布失败，都继续使用此前成功的版本。

页面上提供：

- **组件筛选**：全部、SDK、mcBLAS、mcDNN、PyTorch 等。
- **平台筛选**：CPU 架构、OS、GPU 芯片，以及需要的 Python/PyTorch 配置。
- **App 清单**：默认每个 App 一行，显示所用 App 版本、来源 HPC 发布周期、镜像数、测试项数。
- **展开明细**：每个构建对应的镜像 digest、平台、测试项、完整命令。
- **复制命令、导出测试清单**；以后再增加创建测试批次和记录结果。

这样，“全部组件”就是原来的基线总表，“选择某组件”就是原来的组件兼容清单。

**组件依赖应帮助 QA 找到测试对象，不需要再成为一套独立的兼容验证页面。** 对未声明依赖的 App，应单列“范围待确认”，避免它们被筛选时悄悄遗漏。

### 2. 发布记录：用于追溯某一次发布

提供按 **发布周期、App、镜像 digest** 查找的能力，打开同一种发布详情。

这个入口回答的是：

- 这个 App 在某次发布时是什么状态？
- 这个镜像当时对应哪些平台和测试？
- 当时用了什么命令、得到什么发布 QA 结论？
- 发布后来有没有被更正或撤销？

**兼容性验证页中的每个 App，都可以直接跳到它所引用的那次发布记录。** 两个页面共用同一份数据和详情组件。

## 三、要保证“命令一模一样”，目前还缺一个关键环节

最新代码已经修正了上一轮提到的依赖来源问题：正式版兼容验证现在从正式版 app_info 读取依赖，这点是对的。

但现在的完整命令仍然是在查询时，通过：

**历史 app_info ＋ 正式镜像 ＋ 测试排除项 ＋ 当前命令生成代码**

重新生成的。两处页面都调用 `published_commands()`，它又调用当前的 `docker_cmd()`。[命令生成实现](https://github.com/zzwz02/hpc-release-system/blob/5ed6d76a67419438ed00f6f7ff9cdc26e5f6c5cc/app/domain/delivery_images.py#L41)

这意味着以后修改 Docker 默认参数、平台匹配规则或命令拼接方式，**历史页面生成出来的命令也可能变化**。

所以，对于你明确提出的“一模一样”，我建议：

### 每次发布时，封存一份完整的发布测试清单

| 应封存的信息 | 具体内容 |
|---|---|
| 发布身份 | App、App 版本、HPC 发布周期、发布记录 ID、发布时间 |
| 配置来源 | 当时的 app_info、对应 commit、依赖组件及配置 |
| 交付镜像 | 完整镜像引用与 digest，关联具体构建 |
| 平台范围 | OS、CPU 架构、GPU 芯片、Python/PyTorch、release/dbg |
| 测试清单 | 当次纳入的测试项、排除项、测试与镜像／平台的对应关系 |
| **最终命令** | **完整展开的 Docker 命令原文**，包括容器参数、环境变量、挂载等 |
| 原发布 QA | 当时的结论、备注；后续可补日志和逐项结果关联 |

以后查询、复制和导出，直接读取这份清单。若要更正发布，就新增一个修订记录，保留原记录。

**实现上不需要再建一套庞大的“兼容基线系统”。** 可以继续使用已有 `official_versions` 的发布 ID，在该记录上补充版本化的测试清单 JSON。当前发布记录已经保存 app_info 引用和镜像，补齐最终测试范围、命令和原发布 QA 即可。[当前发布保存内容](https://github.com/zzwz02/hpc-release-system/blob/5ed6d76a67419438ed00f6f7ff9cdc26e5f6c5cc/app/services/cycle_service.py#L799)

还需要明确：当前代码中的 CPU 信息主要是 **CPU 架构**，GPU 信息是配置声明的适用范围；已有 QA 结论是 App 级别，暂时不能据此声称每一个列出的平台都实际测试通过。未来逐平台结果可以单独补充。

## 四、digest 查询和未来 QA 状态，也应围绕这份记录组织

### digest 查询优先查发布记录

现在页面上的 digest 查询会访问 Harbor，通过 tags 定位 commit，再从 Gerrit 读取历史 app_info 重建命令。这个功能适合查任意历史镜像，但它没有应用某次发布排除的测试项，不能完整代表那次发布采用的清单。[当前 digest 查询](https://github.com/zzwz02/hpc-release-system/blob/5ed6d76a67419438ed00f6f7ff9cdc26e5f6c5cc/app/services/lookup_service.py#L65)

建议调整为：

1. **有发布记录：** 返回对应的发布测试清单。
2. **同一 digest 对应多次发布：** 列出各次记录，允许选择。
3. **没有发布记录：** 再通过 Harbor/Gerrit 还原，并明确标为“根据历史配置生成”。

### 未来的兼容 QA 结果，单独记录

需要区分两个事实：

- **发布 QA 结论**：这个 App 当时发布时的结果，保存在历史记录中。
- **本轮兼容验证结果**：使用这份历史镜像和测试清单，在新的组件版本、环境下测试得到的结果。

例如验证 SDK R1 时，应记录“引用哪份发布清单、实际测试环境、本轮结果”，不能覆盖原发布 QA。创建测试批次后也要固定所选发布记录，避免测试期间 App 发布新版，清单自动换成另一套镜像和命令。

如果被测组件位于容器内部，还要记录新组件如何替换及实际使用的版本；命令引用的数据集、外部脚本也应有版本信息。这些可以随未来执行结果功能补充。

**这次可以先完成三项明确改动：合并两个兼容性入口；统一最近成功发布的选择和查询逻辑；在发布记录中封存最终测试清单。** QA 批次和逐项状态留到下一步，先把未来测试必须依赖的历史依据保存完整。
