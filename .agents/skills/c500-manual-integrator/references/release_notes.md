# 发布说明：变更与完整列表

用于 MACA / X201 HPC release notes。目标文件路径与导出入口见上级 [SKILL.md](../SKILL.md)，类型与模块归属见 [classification.md](classification.md)。以下约定适用于这两份发布说明，不改变用户手册的历史内容保留规则。

## 来源与发布口径

先明确用户指定的数据库、目标周期、比较基线和文档芯片范围。只读查询对应快照，逐版本核对发布决策、类型、模块和芯片；同名数据库文件也可能被更新，后续要求重新查询时不能只复用之前导出的结果。生成产物可能因生成时间、Owner确认或文档缺项而遗漏条目，不能代替当前快照的完整发布决策。

- `release_decision=release` 的条目均按发布处理，按芯片范围进入发布列表。不以 `owner_confirmed`、文档完整性、`missing_items` 或QA状态排除条目，也不另设“待确认发布条目”或添加“尚不满足文档确认条件”等限制。
- `stopped`、`cicd_only` 不进入本期发布列表。若基线为发布、本期转为这两类，变更统一写“停止<版本>版本发布”，不把“转为仅CICD，不再列入发布”写进面向读者的说明。
- 快照或生成文档中缺席本身不是停止证据。先核对显式决策与基线，不能把缺项自动写成停止发布。
- 上述发布口径不代表QA通过或数据库周期已锁定。不得编造测试结果、交付包号和软件栈版本；来源状态在工作记录中说明，不用它另设用户未要求的条目筛选门槛。

## 两张表的职责

`新增特性及变更` 列出相对基线的增删改；`HPC发布列表` 列出目标周期的完整发布情况。保留历史变更章节。一次修改措辞、排序或单元格样式时，基于当前文件局部修改，不能从旧生成脚本或Git基线重建而丢失用户已确认的修改。

### 变更措辞

- App首次发布：核对App身份、别名、可用历史快照与历史文档，确认此前没有已发布版本时，写“首次发布<版本>版本，支持<完整芯片列表>”，例如cuOpt。不能用“新增发布”代替“首次发布”，也不能仅因上一周期缺席就断言首次发布。
- 已有App新增版本：写“新增<版本>版本发布，支持<本版本在本文档范围内的完整芯片列表>”。已有App的新版本即使此前已进入CICD，只要基线未发布，也按新增版本描述；若这是整个App的第一次发布，则按“首次发布”描述。
- 版本更新：写“<旧版本>版本更新为<新版本>，支持<新版本的完整芯片列表>”。首次发布、新增版本或更新都必须说明支持范围，不能只写“更新为v3.4.1”，也不能仅列出相对旧版本增加的芯片。
- 新版本没有已发布的同版本基线，不能把旧版本的支持范围套给新版本，写成“新版本新增支持／停止支持／不再支持某芯片”。新版本直接陈述支持范围；确有停止的旧版本另写“停止<旧版本>版本发布”。ARM CPU支持变化同样不能跨版本误比。
- 同一个已发布版本在两个周期都发布时，才比较其芯片和ARM CPU支持差集，分别写“<版本>版本新增支持…”、“<版本>版本停止支持…”或明确ARM CPU支持的变化。
- 同一版本此前已在另一芯片范围发布、本期扩展到本文档范围，写“<版本>版本新增支持<芯片>”，不能误写成新增版本或首次发布App。恢复发布须有此前停止的证据。
- 旧版本继续发布属于未变化事实，不写“保留<版本>版本发布”；继续发布的版本自然保留在完整发布列表中。
- 停止某版本不等于停止整个App。避免“发布/更新所有App”等不可逐项核对的概述；每条变更关联到App身份、版本与两个周期的证据。

以下是措辞示例，具体版本和芯片须重新查询目标周期，不能作为固定数据复用：

| 场景 | 写法示例 |
| --- | --- |
| App首次发布 | cuOpt：首次发布beta版本，支持C500、C600、N300、X301、X302。 |
| 旧版本调整芯片，同时新增版本 | Slurm：22.05.3版本新增支持C588、C600U；22.05.3版本停止支持X206；新增25.05.8版本发布，支持C500、C588、C600、C600U、N300、X301、X302。 |
| 更新版本 | ESM3：v3.2.4版本更新为v3.4.1，支持C500、C600。 |
| 停止旧版本、新增另一版本 | OpenLB（MACA）：停止1.7r0版本发布；新增1.9r0版本发布，支持C500、C600、X302。 |
| 基线发布、本期仅CICD | DiffDock：停止v1.1.3版本发布。 |
| 已有版本扩展到X201 | OpenFOAM（X201）：v2206版本新增支持X201。 |

用户指出某个App的措辞问题时，检查两份文档全部本期条目中的同类问题，不只改示例App。

### 发布列表与排序

- 两份文档均按“科学计算应用、工具、AI for Science模型与框架”的现有分节组织。每个分节的发布列表按类型升序，同类型按名称升序（英文忽略大小写）；按规范化后的显示类型排序，不只按名称排序。
- 同App的多个版本在同一行以 `、` 分隔并自然排序。各版本芯片、ARM CPU或环境有差异时标明对应版本，不能把支持范围取并集后套给所有版本。
- 两份文档的本期变更表按模块归组，沿用“HPC APP、工具、AI for Science模型与框架”的顺序；模块内按应用/模型名称升序（英文忽略大小写）。类型和模块都按当前数据库重新核对，具体映射见分类参考。

## MACA 与 X201

- X201发布列表支持芯片列按既有样式写X201；新增/更新说明也只写本版本的X201范围，不夹带MACA芯片。遇到具体芯片变体先核对定义与来源，不凭前缀猜归属。
- MACA排除X201-only条目；双范围条目只保留对应版本有依据的MACA芯片。新增/更新说明和发布列表使用同一范围。
- 芯片系列映射沿用已有依据，例如X301/X302、C500/C588、C600/C600U、N260/N300；不能为了匹配历史排版擅自扩大支持范围。

## 发布列表与数据库对比（每次必做）

每次处理这两份发布说明（修改、检查或仅回答相关问题），都要把两份文档最后的 `HPC发布列表`（科学计算应用、工具、AI for Science模型与框架三节）与数据库目标周期快照中 `release_decision=release` 的条目逐项对比，并在交付说明中报告结果；无差异也要说明已对比。

- 只读查询当次数据库（`mode=ro`），不复用之前导出的结果。对比条目覆盖、`支持芯片系列` 与 `ARM CPU支持情况`；不考虑文档完整性和QA结果。
- MACA表对应快照 `x86_chips` / `arm_chips` 去掉X201后的芯片；X201表对应其中的X201，ARM列 `true` 表示 `arm_chips` 含X201。
- X201-A不参与对比：数据库有X201-A而文档未列，不算差异。
- 按App身份和版本匹配，多版本合并行按对应版本核对，不能只比较名称。
- 分别列出：文档多出（数据库本期非release，附当前决策）、文档缺失、芯片或ARM不一致。差异不一定是文档错误，数据库决策也可能改错；附上决策和审计记录，由用户判断，不自动改任何一方。

## 跨行表格与验收

使用目标RST的 `.. table::` 网格表，保留 `:widths:` / `:class:`、标题层级及文档风格。变更表参考3.8.0，将同一模块的第一列合并为跨行单元格：

- 模块名称只出现在该组第一行，后续行的首格留空。
- 组内行分隔线在第一列使用空白，第二列起仍使用横线；模块切换及表格结束时使用完整横线。
- 按中文显示宽度补齐单元格；长说明折行不能打断跨行边界。不能只清空重复模块文字却保留首列横线，那仍是独立单元格。

验收时核对：发布决策覆盖、类型与模块来源、两种排序规则、多版本芯片隔离、首次发布与已有App新增版本的区分、首次发布/新增/更新的完整芯片范围、所有“新增支持/停止支持”是否有同版本基线，以及是否残留文档确认门槛、仅CICD措辞或“保留发布”冗余。确认历史章节和本次范围外的用户修改未被覆盖。

对实际修改的Sphinx项目执行严格构建（`sphinx-build -W`，或渲染脚本 `--strict`），检查表格、链接和渲染警告。涉及跨行时检查生成HTML的 `rowspan` 是否对应模块条目数。区分已有与新增警告，不自动忽略新增警告。本地构建不代表对外发布。
