# 发布说明

用于 MACA / X201 两份 HPC release notes。每份有两张主表：`新增特性及变更` 写本期相对上一期的增删改，`HPC发布列表` 写本期完整的发布情况。数据来源、App 身份和芯片范围的通用规则见上级 [SKILL.md](../SKILL.md)。发布说明定稿后如需写 wiki 发布页，见 [wiki.md](wiki.md)。

## 流程

1. `git fetch`，从 `origin/dev_pde` 建本期工作分支 `HPC/<版本>`，在已发布文本上修改。
2. 只读查询目标周期和上一周期的快照，逐版本取发布决策、类型、文档归属和芯片。
3. 确定比较基线（见“比较基线”）。
4. 在往期变更章节之前新增本期变更章节，更新概述和交付内容里的本期版本号。
5. 按本期快照刷新发布列表。
6. 做“发布列表与数据库对比”和严格构建，写交付说明。

已发布的内容不允许修改。发布说明每期只做两类改动：新增本期的变更章节，更新最后的发布列表（汇总表）；概述和交付内容里随周期变化的本期版本号按“其余内容”一节更新。往期变更章节一个字符都不动，发现写错也只在交付说明里报告。

同一周期内后续再调整本期内容的措辞、排序或单元格样式时，在当前文件上局部修改，不从生成脚本或 Git 基线重建，以免丢掉用户已确认的修改。

## 发布口径

- `release_decision=release` 的条目都按发布处理，按芯片范围进入发布列表。不以 `owner_confirmed`、文档完整性、`missing_items` 或 QA 状态排除条目，也不另设“待确认发布条目”之类的限制。
- 本期不是 `release` 的版本（`stopped`、`cicd_only`，或系统里找不到）不进入本期发布列表，处理只看它在不在上一期已发布的发布列表里：
  - 在：本期变更写“停止<版本>版本发布”，并从发布列表删除。不把“转为仅CICD”写进面向读者的说明；系统里找不到的另在交付说明里指出。
  - 不在：不写变更，发布列表也不动。
- 暂时停止发布不等于停止发布。某版本本期因故暂不发布、决策仍是 `release` 时，变更写“暂时停止<版本>版本发布”，发布列表保留该条目；之后恢复时变更写“恢复<版本>版本发布，支持…”，发布列表继续保留。
- 产物里缺席不是停止的证据，产物可能少条目；是否发布以快照的发布决策为准。
- 按发布决策纳入不代表 QA 通过或周期已锁定。不编造测试结果、交付包号和软件栈版本；来源状态写在交付说明里。

## 比较基线

变更是写给读者看的，基线是上一周期**已发布**的发布说明，不只是数据库上一周期的快照。数据库锁定后文档仍可能调整，例如暂停某个 App，或收窄某个版本的芯片范围。

- 每次都把已发布文档最后的发布列表和数据库上一周期快照的 `release` 条目对比（条目、版本、芯片、ARM）。一致时两者等价；不一致时以已发布文档为基线计算本期变更，并在交付说明里逐条列出差异和它对变更措辞的影响。
- 例：某版本数据库两期为 C500、C600、X302 → C500、C600、N300，已发布文档只写了 C500。本期写“<版本>版本新增支持C600、N300”，不写“停止支持X302”。
- 例：某版本数据库两期都是 release，已发布文档的上一期变更写了“暂时停止<版本>版本发布”。本期写“恢复<版本>版本发布，支持…”，发布列表里保留该条目。

## MACA 与 X201 范围

- MACA 文档取快照 `x86_chips` / `arm_chips` 去掉 X201 和 X201-A 后的芯片，排除只支持 X201 的条目。
- X201 文档的支持芯片列按既有样式写 `X201`；ARM 列写 `true`（`arm_chips` 含 X201）或 `无`。变更说明也只写 X201 范围，不夹带 MACA 芯片。
- X201-A 不写入发布说明：两份文档的变更表和发布列表都不出现它，计算变更和做发布列表对比时先从快照芯片里去掉。数据库有 X201-A 而文档未列不算差异。
- 遇到具体芯片变体先核对定义和来源，不凭前缀猜归属。芯片系列的对应沿用已有依据（如 X301/X302、C500/C588、C600/C600U、N260/N300），不为了匹配历史排版扩大支持范围。
- 变更说明和发布列表使用同一范围。

## 类型与模块

- 类型列原样使用目标周期快照的 `type`，即发布系统中的类别，不做映射。
- 模块由 `doc_target` 决定：`manual` 归“HPC APP”，对应发布列表的“科学计算应用”一节；`ai4sci` 归“AI for Science模型与框架”。`type` 不属于其 `doc_target` 类别清单的，在交付说明里指出，不自行改归属。
- `type` 为空时在交付说明里指出缺口，不凭名称补类别，也不因此排除发布条目。
- `doc_target` 变化只让 App 换分节，不产生变更条目；这类移动在交付说明里指出。
- 数据库之后补齐或修正类型时，同步刷新两份发布列表和本期变更表的模块归属。

## 变更表

### 措辞

- App 首次发布：核对 App 身份、别名、历史快照和历史文档，确认此前没有已发布版本，写“首次发布<版本>版本，支持<完整芯片列表>”。不用“新增发布”代替“首次发布”，也不能只因上一周期缺席就断言首次发布。
- 已有 App 新增版本：写“新增<版本>版本发布，支持<本版本在本文档范围内的完整芯片列表>”。新版本即使此前已进入 CICD，只要基线未发布，也按新增版本写。
- 版本更新：写“<旧版本>版本更新为<新版本>，支持<新版本的完整芯片列表>”。
- 首次发布、新增版本和更新都要写完整支持范围，不能只写“更新为v3.4.1”，也不能只列相对旧版本多出的芯片。
- 新版本没有同版本的已发布基线，不能把旧版本的支持范围套给它，写成“新版本新增支持／停止支持某芯片”。新版本直接陈述支持范围；确有停止的旧版本另写“停止<旧版本>版本发布”。ARM CPU 支持同样不能跨版本比较。
- 同一个版本两期都发布时，才比较芯片和 ARM CPU 支持的差集，写“<版本>版本新增支持…”“<版本>版本停止支持…”“<版本>版本新增／停止…的ARM CPU支持”。
- 同一版本此前已在另一芯片范围发布、本期扩展到本文档范围，写“<版本>版本新增支持<芯片>”，不写成新增版本或首次发布。
- 恢复发布要有此前停止的证据，例如已发布文档里的“暂时停止”。
- 旧版本继续发布不写“保留<版本>版本发布”；它自然留在发布列表里。
- 停止某版本不等于停止整个 App。不写“发布/更新所有App”这类无法逐项核对的概述；每条变更都能对应到 App 身份、版本和两期的证据。

措辞示例，其中的版本和芯片要按目标周期重新查询，不能当作固定数据：

| 场景 | 写法示例 |
| --- | --- |
| App 首次发布 | cuOpt：首次发布beta版本，支持C500、C600、N300、X301、X302。 |
| 旧版本调整芯片，同时新增版本 | Slurm：22.05.3版本新增支持C588、C600U；22.05.3版本停止支持X206；新增25.05.8版本发布，支持C500、C588、C600、C600U、N300、X301、X302。 |
| 更新版本 | ESM3：v3.2.4版本更新为v3.4.1，支持C500、C600。 |
| 停止旧版本、新增另一版本 | OpenLB（MACA）：停止1.7r0版本发布；新增1.9r0版本发布，支持C500、C600、X302。 |
| 基线发布、本期仅 CICD | DiffDock：停止v1.1.3版本发布。 |
| 已有版本扩展到 X201 | OpenFOAM（X201）：v2206版本新增支持X201。 |
| 已发布文档曾暂停，本期恢复 | QUDA：恢复2024.1.15版本发布，支持C500、X301。 |

用户指出某个 App 的措辞问题时，检查两份文档本期全部条目里的同类问题，不只改被点名的那个。

### 归组与格式

- 按模块归组，顺序为“HPC APP、AI for Science模型与框架”；模块内按应用/模型名称升序，英文忽略大小写。
- 使用目标 RST 的 `.. table::` 网格表，保留 `:widths:` / `:class:` 和标题层级，格式参照文档里最近一期的变更表。
- 同一模块的第一列合并为跨行单元格：模块名只出现在该组第一行，后续行首格留空；组内行分隔线的第一列用空白、第二列起用横线；模块切换和表格结束处用完整横线。只清空重复的模块文字却保留首列横线，仍是独立单元格。
- 单元格按中文显示宽度补齐；长说明折行不能打断跨行边界。

## 发布列表

- 分“科学计算应用”和“AI for Science模型与框架”两节。
- “科学计算应用”六列：名称、类型、描述、对应官方版本、支持芯片系列、ARM CPU 支持情况。数据库描述为空时保留文档已有的描述。
- “AI for Science模型与框架”六列：名称、类型、对应官方版本、支持芯片系列、ARM CPU支持情况、开发者社区发布情况。
- `开发者社区发布情况` 取快照 `community` 的 `image_count` / `pkg_count`，写“镜像”“镜像、二进制包”或“无”。它由 app_info 的 `pub` 标记推导；相比上一期消失的条目在交付说明里指出。
- 每节按类型升序（Unicode 码位顺序，英文在前），同类型按名称升序（英文忽略大小写）。
- 同一 App 的多个版本写在一行，版本自然排序、以 `、` 分隔。各版本的芯片或 ARM CPU 支持不同时标明对应版本，不能取并集后套给所有版本。

## 其余内容

- 概述、交付内容和本期变更标题里的版本号，在交付包号确定前写 `<版本>.x` 占位（`HPC V3.10.0.x`、`MACA 3.10.0.x Driver软件栈`），不沿用上一周期的具体包号。
- 交付内容里指向发布列表的一条写“科学计算应用、AI for Science模型与框架”，和发布列表的分节一致。
- `已知问题和使用限制` 来自 QA 结论。目标周期还没有 QA 结果（`qa_status=not_checked`）时保持原表不动，在交付说明里指出它仍是上一周期的内容，以及其中哪些 App 本期已停止发布；不根据发布决策自行删改。
- 概述里的适用产品清单没有依据时不改。`preamble.sty` 的日期和文档编号由文档组维护，不改。

## 发布列表与数据库对比（每次必做）

每次处理这两份发布说明，包括修改、检查或只是回答相关问题，都把两份文档最后的 `HPC发布列表` 和数据库目标周期快照里 `release_decision=release` 的条目逐项对比，并在交付说明里报告结果；没有差异也要说明已对比。

- 只读查询当次的数据库，不复用之前导出的结果。
- 对比条目覆盖、支持芯片系列和 ARM CPU 支持情况，范围按“MACA 与 X201 范围”一节；不考虑文档完整性和 QA 结果。
- 按 App 身份和版本匹配，多版本合并的行按对应版本核对，不能只比名称。
- 分别列出：文档多出的（数据库本期不是 release，附当前决策）、文档缺失的、芯片或 ARM 不一致的。差异不一定是文档错，数据库的决策也可能改错；附上决策和审计记录由用户判断，不自动改任何一方。

## 验收

- 对两份发布说明做严格构建（渲染脚本 `--only maca_hpc_release_notes --only x201_hpc_release_notes --strict`，或直接 `sphinx-build -W`），应为零警告。
- 检查生成 HTML 中本期变更表的 `rowspan` 是否等于各模块的条目数，发布列表各节的行数是否等于数据库本期范围内的 App 数。
- 逐项核对：发布决策覆盖、类型和模块来源、两种排序、多版本芯片隔离、首次发布和新增版本的区分、首次发布/新增/更新是否写了完整芯片范围、每个“新增支持/停止支持”是否有同版本基线，以及有没有残留的文档确认门槛、仅 CICD 措辞或“保留发布”。
