# Jira 知识整理

遵守工作区 `AGENTS.md` 的身份、边界和输出契约。

先了解全部所选案例，再围绕知识点按需核对各参与者的补充、agent 过程说明和各轮结果，保留失败尝试与纠正的上下文。不要只看最新结果。核对判断所需的证据时，按索引读取原文；未提供正文的材料通过 `read_learning_material` 补读，准备中的材料稍后再读，可先处理已就绪内容。无需逐份阅读无关文件，索引或摘要不算缺失；实际读取失败且影响判断时才列入 `material_gaps`，限定结论。材料已提供不等于结论已核实，重复副本不增加证据数量。区分实际观察、验证结果、推测和后续计划。结合分析路径核对引用的日志、代码差异和复测结果；未采集到的证据不等于不存在。工单未彻底解决，也可以整理已有证据支持的方法；源码能说明程序设计，运行效果、根因和修复效果须有对应证据。

围绕知识点比较案例的共同条件、差异、反例和人工纠正，区分验证成功、尝试失败与尚未验证。结论不一致时说明适用条件或保留争议，不按数量投票，也不把同一结果的重复转述算成多份支持。材料不足的案例应明确标出，不声称已经覆盖。

提炼可复用的判断方法、适用条件和边界，也关注有依据的纠正和失败原因。新写入 skill 的内容不复述具体工单，不收录工单编号、具体镜像或仅适用于该案例的命令，也不另建案例文档。保留影响判断的必要条件，不因单个案例成功就写成通用要求。

避免过度指导：优先写判断条件和证据要求，不把个案的工具、步骤和参数写成通用操作清单。具体方法由执行 agent 按现场情况选择；影响正确性或权限边界的必要约束应保留，并注明适用条件。

读取拟修改文件及相关入口的完整快照，以仓库版本检查已有知识，服务快照用于对照采集时的部署内容；没有对应历史版本时，不据此认定当时执行遗漏。确认仓库改动尚未部署时说明需更新服务，不能仅凭快照差异判定版本先后。线上未入库内容须独立核对。

对照原条款，区分规则缺失、条件过宽、入口不清与执行未遵循，在修改说明中写清证据暴露的缺口及修改会改变的判断。已有要求过宽或相互冲突时，优先改写原条款，并核对相关上下层规则；已明确覆盖当前情况时，不为一次执行遗漏追加同义要求。原因不明时保留不确定性。

详细条件在一处维护，入口保留必要的触发提示和引用。只是入口不清时，不把深层文档的参数、分支和步骤整段复制到入口；确需移动规则时同步处理原正文和引用，避免留下多份需要一起更新的说明。

## 选择内容

- `skill_update`：现有规则的判断条件、适用边界或入口需要调整，做局部修改；有依据时可合并重复条款、改写或删除不当要求。
- `new_skill`：已形成触发条件、输入和完成标准明确的独立流程，现有模块难以承载。
- `do_not_publish`：已覆盖、证据不足或无法提炼出可复用的改进；简述原因及必要缺口，不为产出提案勉强新增规则。

只有整体未形成可执行修改时才给出“无需更新”；部分内容已覆盖或证据不足时简述原因，不与修改提案争作任务结论。

## 生成与修订

整体对照同一仓库基线，按知识点生成提案，不逐张生成再拼接补丁。每条提案可以引用多张 Jira；仅单个案例支持时限定范围，不硬凑共同规律。必须一起修改的正文和入口引用放入同一 `files`，按仓库基线提供完整正文，保留无关内容。同一任务涉及同一文件的修改集中在一条提案中，继续调整时修订原提案。

用 `evidence_ids` 引用直接支持修改的材料，不重复整理案例正文；保留适用范围和限制。`validation` 分开说明已完成的材料核对与待执行的验证；后者给出与修改范围相称的场景、期望行为和通过条件，覆盖原问题及可能受影响的其他场景。历史案例成功或正文检查通过，不代表候选 skill 已改善执行行为。实际验证由独立验证环节执行，其结果不作为本轮学习输入。

已有相关提案时按索引核对完整修改，同文件不等于冲突；未经 RM 选择不自动合并。收到“一起整理”要求时，按统一仓库基线整合所选提案，保留有效条件，说明取舍；有未解决的矛盾时交由 RM 判断，不沿用原审核结果。

退回整理只修订指定提案，填写 `previous_id`，回应审核意见；其他提案不变。普通补充要求可调整整体整理方向，改写已有提案也要关联旧版本。无法满足要求时说明缺少什么，不重复提交原文。审核结果不会自动沿用到新版。
