# JIRA Bug 分类与归属判断

## 1. 收集信息

- 阅读 `issue.md`：摘要、描述、组件、评论（按时间顺序，注意评论中的补充要求，例如指定机器、复现步骤）。
- 列出 `attachments/` 和 `uploads/`，逐个查看源码、日志、构建脚本。
- 整理出：期望行为、实际行为、复现命令、运行环境（机器、GPU、驱动和工具链版本）、验收标准。
- 缺少关键信息（无法确定复现方法或验收标准）时，先尝试从附件推断；推断不出来再给出 `needs_info`，并具体列出缺少什么。

## 2. 分类

从下面选一个主类别写入 `issue_category`，可以附简短说明：

- 编译 / 构建失败
- 运行崩溃 / 挂起
- 结果错误 / 精度问题
- 性能问题
- 环境 / 驱动 / 工具链问题
- 用法 / 文档问题

## 3. 归属判断

`ownership.belongs_to_us` 取以下三个值之一，必须在 `reasoning` 中写明依据（引用具体的代码位置、日志行或复现结果）：

- `yes`：问题位于 HPC 应用自身的源码、构建脚本或运行脚本中，HPC 组可以修改和验证。
- `no`：根因位于其他组负责的组件。以下为常见去向示例，由 HPC 组维护补充：
  - 框架算子、PyTorch 相关报错 → PyTorch 组
  - 驱动、内核模块、设备管理工具 → 驱动 / Runtime 组
  - 编译器或 cu-bridge 工具链自身崩溃、生成错误代码 → 编译器 / 工具链组
  - 集合通信库 → 通信库组
- `unclear`：证据不足以判断。写清已经排除的可能性和还需要的证据。

归属判断可以随着分析深入而改变；以最终证据为准。

## 4. 决定下一步

- `yes` → 使用 `hpc-bug-repro`。
- `no` 或 `unclear` → 在可用资源内尽量复现以提供证据，然后使用 `cross-team-handoff` 整理交接材料。
