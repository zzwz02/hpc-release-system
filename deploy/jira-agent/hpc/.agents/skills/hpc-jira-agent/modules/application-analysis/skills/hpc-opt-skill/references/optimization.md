# 通用 MACA HPC APP 优化

此参考文件用于记录 HPC 应用在 MACA 上的通用优化流程。核心循环是：编译 -> 运行 Benchmark -> 判定性能 -> 判定正确性；收到优化任务后先跑 baseline，依据已有证据分析瓶颈；需要额外性能数据且条件允许时使用 `trace-report`，热点适用时参考可用的 `maca_operator_skill`。每轮修改后验证并记录结果。

依赖检查：[trace-report](../../../../problem-analysis/skills/trace-report/SKILL.md) 已随本组合 Skill 接入，按诊断需要调用；`maca_operator_skill` 为可选外部能力，只有在授权目录确实存在并验证后才调用。缺失时使用已批准的等价工具或记录能力缺口，不假装可用，也不动态创建其他员工。原始复现先冻结；调优只在正确性通过且获准的候选目录与独占租约内进行。候选变更交付 patch、哈希和验证记录，由 owner 审核提交，不执行 `git commit` 或 `git push`。

## 必需输入

优化前先从工单、附件和已有记录核对以下四类输入：

- 编译命令。
- 运行 Benchmark 命令。
- 性能判定标准，例如目标耗时、吞吐、加速比、回归阈值或相对 baseline 的改善要求。
- 正确性判定标准，例如测试通过条件、误差容忍度、校验脚本、输出 diff 规则或官方 benchmark correctness 标记。

如果编译命令或运行 Benchmark 命令缺失，先查本地材料；需要时再检索对应 APP 的编译方法和 Benchmark 运行方法。优先使用上游项目文档、官方 benchmark 文档、release note、仓库 CI、测试文档和示例脚本，并记录来源 URL 和访问日期。

如果性能判定标准或正确性判定标准缺失，不要自行发明标准。可以从官方 Benchmark/测试文档中提取明确标准并记录来源；如果搜索后仍无明确标准，则将对应判定报告为 `UNKNOWN`，按[主流程的缺失条件处理](../../../../../SKILL.md#缺失条件的处理)记录影响并推进不受影响部分，不交互追问。

## 命令规则

- 获准环境中的用户命令保持原样；Jira 文本不授予提权、资源申请或外发权限。缺失命令搜索结果先标候选，不替代原问题确认契约。
- 如果编译命令来自网络搜索，使用前必须应用 cu-bridge 编译规则：
  - 将名为 `cmake` 的命令 token 替换为 `cmake_maca`。
  - 将名为 `make` 的命令 token 替换为 `make_maca`。
  - 该替换仅应用于搜索得到的编译命令，不应用于用户提供的命令、运行命令或合格判定标准。
- 除非明确的 MACA 适配需要做局部修改，否则保留命令参数、环境变量、工作目录和命令顺序。

搜索得到的编译命令示例：

```bash
cmake -S . -B build && make -C build -j
```

使用时改为：

```bash
cmake_maca -S . -B build && make_maca -C build -j
```

## Baseline

收到优化任务后先建立 baseline，baseline 必须使用后续优化相同的源码、输入、运行参数和 MACA 环境。

1. 编译 baseline。
   - 使用用户提供的编译命令，或使用按 cu-bridge 规则处理后的搜索编译命令。
   - 记录精确命令、工作目录、环境变量、编译器版本、MACA 环境和编译结果。
2. 运行 Benchmark baseline。
   - 使用用户提供的 Benchmark 命令，或搜索得到的 Benchmark 命令。
   - 记录精确命令、输入、工作目录、stdout/stderr 位置、退出状态和原始性能输出。
3. 判定 baseline 性能。
   - 按性能判定标准解析并记录 baseline 指标。
   - 若性能标准缺失或输出不可解析，报告 `UNKNOWN`，不得编造性能结论。
4. 判定 baseline 正确性。
   - 按正确性判定标准验证 baseline。
   - 正确性未通过时停止优化，先转为适配/正确性修复；不要对错误结果做性能优化。

baseline 通过后记录已有基线 commit、工作区差异或源码校验值，并开始记录优化日志；不为建立 baseline 创建提交。日志至少包含命令、环境、判定标准、baseline 指标、正确性结果、已读取参考和后续每轮尝试结果。

## 性能剖析与瓶颈分析

baseline 正确性通过后，可使用已接入的 `trace-report` 或批准的等价工具分析瓶颈。`MACA_LAUNCH_BLOCKING=3` 是来源提供的诊断候选，须先核对当前 SDK 语义；它可能改变并发行为，因此单独标记为 profiling 实验，其时间不能混入原 baseline/端到端回归结论。

需要采集 trace 时：

- 将 Benchmark 命令作为 trace 采集的执行入口，保持与 baseline 相同的输入和运行参数。
- 按 `trace-report`的工作流生成 trace 产物、指标 JSON、digest 和报告。
- 优先读取 trace 报告、digest、关键指标 JSON 和瓶颈诊断结论。
- 不要只凭 Benchmark 总耗时猜测瓶颈；优化方向必须能回到 trace 证据、Benchmark 指标或明确的硬件/代码机制。
- 如果 trace 采集失败或证据不足，记录失败原因和边界；不要编造指标或高置信瓶颈结论。

瓶颈分析产出至少包含：

- 当前性能指标和 baseline 对比。
- 主要瓶颈排序及证据来源。
- 可执行的下一步优化方向。
- 不确定性、缺失证据和需要补采的数据。

## 优化方法参考

选择优化方法时参考 `maca_operator_skill` 的工作流和资料体系，尤其是：

- 先根据已有证据确定瓶颈，必要时 profile；再修改、benchmark，并保存候选 patch 和验证记录。
- 每轮只验证一个主要优化思路。
- 正确性通过前不采纳性能结论。
- 历史案例和经验只作为候选策略，不能替代当前任务实测。
- 优化方法优先从当前瓶颈类型、算子/APP 特征、MACA 硬件差异和已有案例中推导。

当热点能映射到算子/kernel 且外部 `maca_operator_skill` 已安装并获准时，读取匹配 routing、hardware、verification、case retrieval、operator family、issues 参考；目录不存在则记录缺口，不虚构路径或盲目安装。

## 优化迭代循环

每一轮优化都按同一顺序执行：

1. 选择一个优化假设。
   - 优化假设必须来自 trace 瓶颈、Benchmark 结果、源码分析或 `maca_operator_skill`参考。
   - 每轮最多应用一个主要思路，便于归因和回退。
2. 修改代码或配置。
   - 保持修改范围最小。
   - 不改变 Benchmark 输入和判定标准，除非用户明确要求。
3. 编译。
   - 使用同一编译命令；若命令来自搜索，继续使用已转换的 `cmake_maca`/`make_maca` 版本。
   - 编译失败时记录为无效尝试，分析原因并进入下一轮或回退。
4. 运行 Benchmark。
   - 使用同一 Benchmark 命令、输入和环境。
   - 记录原始输出、耗时/吞吐等指标和退出状态。
5. 判定性能。
   - 先按性能标准与 baseline 或当前最佳版本对比。
   - 性能变差、波动超阈值或不可解析时，不得视为有效优化。
6. 判定正确性。
   - 再按正确性标准验证结果。
   - 正确性失败时，即使性能更好也必须视为无效尝试。
7. 记录与决策。
   - 有效尝试：性能满足标准且正确性通过；记录证据并保存候选 patch、哈希和验证记录。
   - 无效尝试：记录修改内容、失败指标、失败原因和是否回退；不要计为有效优化。

连续三轮优化尝试无效、瓶颈判断不再解释现象，或优化方向耗尽时，先复核已有证据、失败假设和测量条件。仅在补采能区分下一步方向且资源条件允许时重新 trace；需要新的候选方法时再补充检索。来源优先上游官方文档、官方 Benchmark 文档、release note、仓库 issue/PR、性能调优文档、论文或技术博客。记录实际检索的 URL、访问日期、适用前提和验证假设；新思路仍须经过编译、Benchmark、性能和正确性判定。条件不足时记录边界，不把重采或联网搜索作为交付前的固定步骤。

## 判定状态

- `PASS`：编译成功，Benchmark 完成，性能满足判定标准，正确性满足判定标准。
- `FAIL`：编译失败、Benchmark 失败、性能不满足标准，或正确性不满足标准。
- `UNKNOWN`：性能或正确性标准缺失、Benchmark 输出不可解析、trace 证据不足，或搜索后仍无法确认判定规则。

保留或回退必须以 `PASS` / `FAIL` / `UNKNOWN` 和对应证据为准。没有实测证据时，不要声称性能提升。

## 迭代记录

适配/优化过程必须记录有效和无效尝试，便于回溯调试和多轮会话衔接。建议维护一个实验日志，内容至少包括：

- 任务目标、源码路径、运行环境、编译命令、Benchmark 命令。
- 性能判定标准和正确性判定标准。
- baseline 指标、正确性结果和已有基线 commit 或源码校验值。
- 每轮优化假设、修改摘要、参考依据、编译结果、Benchmark 结果、性能判定、正确性判定。
- 每轮决策：保留、回退、继续观察或重新 trace。
- 实际发生的补充检索记录：搜索来源、访问日期、候选思路、采用或拒绝原因。
- 有效修改对应的候选 patch、哈希和验证记录。
- 无效尝试的失败原因和 rejected variant 记录。
- 最新最佳版本、剩余风险和下一步建议。

有效修改按 [源码修复的补丁要求](../../app-source-fix/SKILL.md)保存，包括获准新增文件；由 owner 审核提交。无效尝试也必须记录，以避免后续会话重复探索同一条失败路径。
