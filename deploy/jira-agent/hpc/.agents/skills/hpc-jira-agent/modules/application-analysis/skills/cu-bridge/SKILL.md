# cu-bridge 应用迁移与诊断

将 cu-bridge 作为 CUDA 源码到 MACA 的构建与接口适配层使用：构建包装器改写编译入口、参数和依赖，兼容头文件与 wrapper 映射 API，设备代码由 MACA 编译器生成。不要由此推断任意 NVIDIA cubin、PTX 或闭源 CUDA 库都能直接运行。

使用这里的构建方法、接口映射与诊断步骤开展工作；涉及版本兼容和具体功能支持时，检查目标环境的安装信息、实际实现与验证结果。

## 1. 确认输入与适用边界

收集或复用应用版本/commit、原始构建命令、必需功能、失败日志、GPU/驱动、MACA SDK 和 cu-bridge 身份，以及原正确性判据。先区分配置、编译、链接、加载、执行、结果校验中的失败阶段。

在 HPC JIRA 部署中遵守当前部署的 `AGENTS.md` 和主流程：只在获准执行机及候选工作目录开展实验；占用 GPU 的操作使用部署规定的锁。原始附件保持不变，应用范围与责任依据已有证据判断。使用本 skill 不授予修改外组 cu-bridge/SDK、共享安装或直接操作 JIRA 的权限。

只需静态分析时输出已确认能力与待验证项，不要求先运行 GPU。目标环境缺失时标明缺口，不把通用映射规则当作目标机已验证的能力。

## 2. 核对实际工具链

- 查 `MACA_PATH`、`CUCC_PATH`、编译器真实路径、SDK 的 `Version.txt` 和 cu-bridge 的源码 tag/commit 或安装来源。`cucc -V` 显示兼容 CUDA 版本，不能作为 cu-bridge 发布版本。
- 保留原始失败后，在独立候选构建目录尝试 `CUCC_CMAKE_ENTRY=2` 与 `CUDA_PATH=$CUCC_PATH`。该模式提供 CMake 探测所需的模拟环境，不证明真实目标编译或运行已通过。
- 每个独立构建任务配置唯一的绝对路径 `CUBRIDGE_HOME`；同一任务的配置和编译沿用该值。核对 `WCUDA_HOME` 是否覆盖它，避免并行任务互相删除临时文件。
- `CUCC_CUDA_VERSION`、CMake 的 CUDA 架构参数和实际 MACA 目标 ISA 各有用途。不能通过伪装版本或架构声明新 API、PTX 指令已经受支持。

具体命令和版本限制见[环境与构建](references/build.md)。

## 3. 沿原构建路线做最小适配

优先复用应用 CUDA 后端及已验证的 MACA 构建配置，根据原入口选择 `cucc`、`cmake_maca`、`make_maca`、`ninja_maca` 或 `pre_makefile`。保留原功能开关、依赖版本与精度要求，不因出现 CUDA/NVIDIA 名称直接更换后端。

先检查包装器是否接管了真实编译和链接命令，再判断是否需要改应用源码。特别检查子工程、硬编码 `nvcc` 路径、外部构建工具和 Python 扩展。区分应用构建脚本遗漏与 cu-bridge 转换缺陷。

## 4. 用证据逐层定位

沿“原编译命令 → 包装器转换后的命令 → 兼容头文件 → wrapper → 实际 MACA 库 → 运行结果”追踪第一个有效错误。

API 支持至少区分：仅有声明、存在映射、链接可用、目标行为已验证。同名符号或库软链接不等于完整语义兼容。遇到 PTX、warp、动态加载或 JIT 时，按[故障定位与兼容性](references/diagnosis.md)缩小问题，不做全局名称替换或批量将 `32` 改为 `64`。

已确认的本组应用问题在候选目录修复；若证据指向外组 wrapper、编译器或运行库，交付最小复现、转换前后命令、版本与符号/行为证据，不跨组修改组件。

## 5. 验证并交付

按需要逐层验证，明确哪层尚未执行：

1. 配置通过；真实目标编译并生成预期产物。
2. 链接和加载使用预期 MACA/cu-bridge 库；动态加载路径另外核对。
3. 最小相关探针验证所需 API、设备代码或库调用。
4. 原应用目标案例满足原正确性和精度判据；探针通过不能代替这一层。
5. 任务要求性能时再按相同输入、设备、并发与计时条件比较。

不得为了迁移通过而放宽精度阈值、删除校验或关闭必需功能。无正确性依据时写“未验证”。

交付：环境和源码身份、原始与候选命令、关键日志/退出码、最小候选补丁、各验证层结果、剩余缺口与责任证据。在本部署中沿用主流程的产物目录和结构化结论，不另造提交或发布流程。
