# GPU SDK 回退分析

目标：找出触发回退的最小版本变化、配置、依赖库组合或执行路径，形成可复核的因果证据。定位深度、修复权限及交付时机遵循[上层回退分析](../regression-analysis/SKILL.md)，不能把规避现象当作根因修复。

## 操作边界

- 按本次授权执行。只读分析不包含启动负载、修改宿主 SDK、推送镜像、重启服务或终止进程。
- 区分跳板机与测试机；GPU 和进程观察在实际测试机执行。使用已有 SSH 配置，不记录密码、令牌、私有 IPC 句柄或完整未脱敏环境。
- 保留原镜像和宿主安装；组件替换使用临时派生容器或只读挂载的候选文件。
- 共享机器上先核对本轮容器、rank、PID 和 GPU。不能用进程名或全局 GPU 利用率判断作业归属，也不能用宽泛的 `pkill` 清理。

涉及跳板机、共享 GPU 或卡死取证时，读[共享环境与卡死取证](references/shared-gpu-host.md)。

## 证据层级

| 层级 | 能够说明什么 |
|---|---|
| 规避方案 | 关闭功能、跳过路径或减少工作量后现象消失 |
| 相关性 | 版本、库或配置与现象一起变化，但仍有未控制变量 |
| 因果触发 | 有效的单变量正反对照支持某项变化触发故障 |
| 根因 | 证据解释了被破坏的约束及实现路径，并能预测其他可验证现象 |
| 候选修复 | 修改实现，保留原故障路径和工作量，等待完整验证 |
| 已验证修复 | 原故障路径重复通过，相关正确性、退出、性能及生命周期检查通过，同条件未修复对照仍失败 |

结论不得超过证据。减少 rank、缩小输入、关闭功能、重试或超时终止都不能直接称为修复；触发条件也可能只是暴露了另一层的潜在缺陷。

## 1. 固定对照条件

分别记录正常组与异常组：

- 镜像引用与不可变 digest、启动命令、容器内实际 SDK 版本。
- 驱动、固件、GPU、rank 数及映射、设备暴露、CPU 亲和性、挂载、输入摘要和用户/组设置。
- 脱敏后的相关环境变量，核对 rank 进程内的实际值。
- 源码 commit、构建选项、编译器/运行时版本、应用二进制摘要和缓存状态。

两组使用独立输出目录和容器名。除本轮实验变量外，命令、输入、设备、rank 和缓存条件保持一致；按需隔离缓存，不删除共享缓存。

## 2. 确认正常与异常基线

先区分性能、卡死/活锁、崩溃、正确性或组合问题。默认对确定性卡死至少独立复现两次，性能每组至少保留三个预热后样本；有波动时增加样本，受成本或授权限制时说明不足。冷启动、自动调优和稳态耗时分开。

保存应用实际退出码，容器内的管道也要把内层状态传出来。例如在 Bash 中：

```bash
set -o pipefail
mpirun ... 2>&1 | tee /artifacts/run.log
code=${PIPESTATUS[0]}
printf '%s\n' "$code" > /artifacts/mpirun.exit
exit "$code"
```

成功判据包括工单要求的输出/数量、正确性、正常收尾及各 rank/容器退出状态；外层 shell 返回 0 不足以证明成功。性能报告保留原始样本和中位数，不把慢运行与卡死混在一组统计。

## 3. 确认本轮进程与 GPU

运行前后记录容器 ID、容器初始 PID、各 rank PID、设备映射和 GPU 工具显示的进程。MetaX 可用 `mx-smi`，具体参数以现场帮助为准。

GPU 忙可能来自其他作业，单次利用率为 0 也不能证明卡死。需结合本轮进程仍存活、日志/进度持续不变和重复栈中的等待关系判断。

## 4. 卡死时先取证再终止

保留带时间戳的多次快照：日志大小和最后进度、GPU 利用率/显存/功耗/进程、各 rank 与线程状态、等待通道、获准采集的栈及 `/proc/<pid>/maps`。对齐各 rank 最后阶段，区分通信、事件、队列或流等待中的进度差异。

超时依据正常基线及已知波动设定。超时后先保存证据，再只终止本轮确切容器或进程。

## 5. 比较实际执行的软件栈

先确认进程实际加载的库，再清点 SDK；源码或版本字符串相同不证明二进制相同。分别在正常与异常环境采集，汇总后比较：

```bash
bash scripts/collect_sdk_manifest.sh <正常环境SDK目录> artifacts/good-sdk.tsv
bash scripts/collect_sdk_manifest.sh <异常环境SDK目录> artifacts/bad-sdk.tsv
python3 scripts/compare_sdk_manifests.py artifacts/good-sdk.tsv artifacts/bad-sdk.tsv > artifacts/sdk-diff.tsv
```

优先分析 `ldd` 和 `/proc/<pid>/maps` 中实际依赖的变化，包括 SHA-256、软链接、Build-ID、SONAME、`DT_NEEDED`、符号版本、主机/设备代码、RUNPATH 和默认配置。替换库或二分 SDK 前读[二进制与组件隔离](references/binary-isolation.md)。

## 6. 用受控实验缩小范围

先检查功能开关和默认配置，再考虑混合版本库。按当前候选选择有区分力的对照：

| 对照 | 目的 |
|---|---|
| 正常版本 + 默认配置；异常版本 + 默认配置 | 确认基线差异 |
| 异常版本 + 正常版本的配置语义 | 检查配置变化是否触发现象 |
| 正常版本 + 异常版本的配置语义 | 在支持时验证反向结果 |
| 异常版本 + 候选修复，保留触发功能 | 验证是否修复原路径 |

配置须在 rank 进程、查询接口或日志中确认实际生效。旧版本不支持新语义时标记该组不可执行，不用 ABI 不兼容的库混搭伪造反向对照。

确需组件替换时，先按职责和 ABI 耦合划分依赖组合，再在可疑组合内二分；每轮只改变一组库或一个配置，核对实际加载路径。由混合版本造成的加载、符号版本或 IPC 句柄不兼容属于无效实验，不能用于归因或排除。

当受控对照已指向 SDK/运行时时，版本范围或库集合只是中间结论。若现有证据和工具允许，继续缩小到能触发现象的最小外部 API 或调用集合，并用正常/异常对照说明；定位到 API 边界即可，不分析内部实现。若可直接从原案例缩减且不改变调用顺序、频率、数据依赖和同步关系，可附最小复现；否则交付最小已验证范围、已排除项与无效实验，以及无法继续缩小的具体原因。

## 7. 验证机制与修复

根因说明须连接版本/配置变化、代码或二进制行为、栈/跟踪结果和原始现象，并给出可证伪的预测。

获准修复时保留原输入、rank、通信模式、调优行为和触发功能，验证重复完成、真实退出码、输出与数值正确性；核对是否隐藏降级、跳过工作或关闭路径。按问题检查预热后的性能、事件/信号/内存/IPC 句柄及进程生命周期，并保留同条件未修复对照。

## 产出

返回正常/异常版本身份、控制变量与实验结果、实际加载库及关键差异、结论证据层级、已排除项和未确认项。共享环境补充本轮资源归属和并发影响；有复现或候选修复时附实际验证材料，证据不足时给出下一项可区分实验。

复用已有记录，保留关键基线、决定性实验和最终验证；只清理本轮已无保留价值且获准删除的产物。报告与评论仍按工程统一交付规范组织。
