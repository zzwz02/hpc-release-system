# 性能问题分析

性能本身是工单需要解决的现象，或性能结果会改变对当前修复和验收的判断时，才进入本专项。测试失败工单中顺带产生的性能值或通用阈值，不自动把本单扩展为性能验收。进入本专项后先核对正确性、指标方向/单位、计时区间和目标来源；不以历史 good/bad 为必需输入，没有明确目标时可以分析开销与瓶颈，但不能自定阈值判“不达标”。工单比较不同硬件或平台的性能时，必须先使用同一发布版本、相同输入、命令和统计口径确认原始差异；原始差异尚未确认时，其他软件版本只能作为探索性对照，不能替代工单基准，也不能用于根因、归属或交接结论。

确需历史性能时，实时查询 [HPC Performance](https://hpctest.swlab.metax-tech.com/d/d7805ec4-0e13-4d52-ab8c-7e95c29d9dcc/hpc-performance?orgId=1)：按 `maca_version`、`chip`、`arch`、`Job`、`testgroup`、`branch` 和 `testcase` 筛选，只比较硬件、案例、分支、ECC、输入/命令、指标单位和 `min`/`max` 方向可比的记录，并记录查询时间。区分历史 `golden`、目标平台 `target_metric` 和 Jira 的验收阈值，面板标记不覆盖工单要求。仍缺少可比基准时，按[总入口规则](../../../../SKILL.md#缺失条件的处理)说明受影响的性能判断并继续其它有效分析，不用本轮候选对照冒充指定基准。

## 测量与定位

1. 按工单原命令和原统计口径复现，记录原始计时分量、计算结果和正确性。诊断中可以增加受控对照，但不能未经确认就用新的统计方式替代原验收指标。
2. 依据工作负载取得足以判断波动的重复样本，保持影响结论的输入、环境和运行条件可比；资源干扰或随机输入存在时，说明其对证据的限制。
3. 确认性能差异后，按实际调用关系拆分 CPU、GPU、加载初始化、数据处理和同步等主要阶段。阶段计时用于解释原指标，不能直接作为新的验收结果。
4. 主要关注 GPU 时，优先确认 GPU 阶段是否确实变慢；只有相关证据支持时，再继续定位具体 kernel、调用次数、累计影响及对应的 AOT 编译信息。若 GPU 阶段没有回退，保留并分析其它阶段的差异，避免错误归因。

差异指向 UMD/运行时 host 路径时，不能只报告组件或阶段范围。写清具体回退现象，并将证据尽量收敛到能够解释差异的最小外部 API 或调用组合，量化调用次数、单次/累计耗时和端到端影响；到 API 边界即停止，不分析 API 内部实现。若无需大幅改写即可从原案例抽出保留相同调用与同步关系的最小复现，可一并交付；否则不强制构造。

MACA 应用出现首次运行异常、重复运行耗时异常或运行期编译线索时，组合 [运行期重编译分析](../runtime-recompile-analysis/SKILL.md)，确认是否实际发生重复编译及其影响；不按应用名称预设该原因。

确认版本或配置变化后再用 [回退诊断](../regression-analysis/SKILL.md) 做受控对照；正确性失败转 [correctness-analysis](../correctness-analysis/SKILL.md)。没有进展先判是否卡死，不直接按普通性能问题处理。

## 分析与改动分离

诊断输出目标/口径、测量样本、热点或瓶颈证据、未排除项与下一实验，不自行把任务升级为算法优化。获得优化授权后，复用 [HPC 优化方法](../../../application-analysis/skills/hpc-opt-skill/SKILL.md) 及应用专项；满足其测量要求，保持正确性与原工作量，并回验端到端收益。不能以降低精度、缩小输入或省略计算形成虚假提升。
