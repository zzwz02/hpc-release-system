# 运行期重编译分析

仅在运行期编译可能解释当前现象时使用。先保存不带额外调试的原始结果；根据实际加载组件确认后端和观测方式，不按应用名称预设，也不猜测日志开关。

## 分析流程

1. 核对原命令、输入、进程边界、SDK/compiler、目标架构、实际加载库和构建配置，确认运行期编译路径。
2. 选择当前版本支持的最小观测方法，优先取得成功编译事件及耗时。应用调试级别、失败日志、缓存文件或 kernel launch 记录都不能单独证明是否发生编译；汇总计时只代表其覆盖的路径。
3. 在相同条件下区分同一进程的首次与后续调用；新进程再次 JIT 不等于同进程重复编译。分析版本变化时，按需对比新旧产物与 runtime；组件组合必须兼容，并核对实际加载身份和结果正确性。
4. 发生重复编译时，比较有效输入、kernel、编译选项、目标架构、组件身份和缓存状态，区分新增编译、同一有效输入重复编译和原有编译变慢。每轮只改变能区分候选的必要变量。
5. 将事件与原现象对齐。只有新增或重复编译的累计耗时能够解释热点或总耗时增量时，才认定它造成性能问题；附加观测的耗时不能替代原始结果，解释不了差值时返回原热点继续分析。

## 结论判断

- 正常首次 JIT：首次发生、同一有效进程内复用，且符合实现边界；
- 进程级 JIT：每个新进程首次生成，但同一进程内能够复用；是否异常取决于实现和性能要求；
- 重复编译或缓存异常：同一进程内相同有效输入再次编译，或应复用条件因缓存问题失效；
- 组件异常或交互问题：受控对照改变编译行为；若产物提供触发条件而 runtime 重复处理，按组件交互描述；
- 与本问题无关：存在编译事件，但其阶段、耗时或对照不能解释原现象，应返回原症状分析路径。

## 交付与边界

交付实际命令与环境、进程边界、编译事件或计时、对原问题的影响、归因深度及尚未确认项；缓存与组件信息只在影响判断时提供。
诊断只使用任务专用缓存或只读观测，不清理或修改共享缓存。
