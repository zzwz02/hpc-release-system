# 二进制与 SDK 组件隔离

正常/异常 SDK 文件有差异、源码看似未变，或准备跨版本替换库时使用。

## 1. 比较实际执行内容

源码相同不代表应用二进制相同；某个库文件相同，也不代表调用方、配置、依赖或分派路径相同。每组记录：

- 镜像 digest 和容器内实际版本。
- 应用/插件摘要、编译器与链接器版本、构建选项、RUNPATH/RPATH，以及嵌入的 fatbin/PTX/SASS 等设备代码。
- 实际负载进程的 `/proc/<pid>/maps`、`ldd` 和加载器诊断。
- SDK 相对路径、软链接目标、SHA-256、ELF Build-ID、SONAME、`DT_NEEDED`、符号版本、导出与未定义符号。

先用[采集脚本](../scripts/collect_sdk_manifest.sh)和[比较脚本](../scripts/compare_sdk_manifests.py)生成清单，再深入实际依赖链及相关文件：

```bash
readelf -h -d -n -Ws -V ./libcandidate.so
nm -D -C --defined-only ./libcandidate.so
objdump -p ./libcandidate.so
ldd -r ./application
sha256sum ./application ./libcandidate.so
```

工具链支持时再比较设备代码清单、资源用量、PTX/SASS 或对应厂商产物。区分调试/ELF 元数据变化与主机 `.text`、`.rodata`、配置数据或设备代码变化。

## 2. 按证据排列候选

优先检查实际加载且位于卡死或慢路径上的变化，按职责和 ABI 耦合分组：

1. 应用、插件和 API 适配层。
2. 高层 GPU 运行时。
3. 底层驱动、队列、事件、信号和命令运行时。
4. MPI、UCX、集合通信及通信插件。
5. 编译器运行时、设备支持和内核库。

文件变化只是候选线索；字节相同的库仍可能被不同调用方或默认配置触发。替换前先检查功能开关和默认值，并通过 rank 环境、查询接口、跟踪或日志核对实际值；正反对照用于区分因果触发与版本相关性。

## 3. 替换兼容的依赖组合

在临时容器或只读候选挂载中执行，不改宿主 SDK。启动 GPU 负载前：

1. 检查架构、SONAME、`DT_NEEDED`、符号版本和未解析符号。
2. 使用 `LD_BIND_NOW=1`、`ldd -r` 或平台等效方法检查动态链接。
3. 将必要软链接和紧密耦合的依赖库作为同一组合替换。
4. 执行一个受控案例。
5. 用 `/proc/<pid>/maps` 确认加载的确为候选文件。

先替换完整功能组，再在命中的组内二分。每种组合保留清单，每轮只改变一个组合或设置。

## 4. 判断对照是否有效

| 结果 | 可支持的结论 |
|---|---|
| 加载、符号版本、对象布局或 IPC 句柄因混合版本不兼容而失败 | 无效混合版本实验，不能据此排除组件 |
| 异常版本替换一个兼容依赖组合后恢复 | 该组合成为因果候选，不能直接归到其中某个库 |
| 反向兼容替换使正常版本出现同一故障 | 加强因果触发证据 |
| 实现路径变化解释栈和被破坏的约束 | 可支持机制根因，仍需核对其他解释 |
| 保留原功能与负载的候选修复通过，未修复对照仍失败 | 支持修复有效 |

整套 SDK 替换失败不能证明各组件均无关；实验后不在宿主遗留混合 SDK。
